The best way to learn is to get your hands dirty and learn along the way. And this book is being written as I plan things. But before you start you should have a clear end goal in mind. For this book and the project I want to take something that seems really mundane and add enough complexity and some more that you go through a discovery of the challenges of building something, iterating over its features and then bringing it to a satisfactory checkpoint at each step.

So what are we building, if you don't already know from the title, we are building a ToDo app. How mundane right? But we are not gonna stop at that. We want to build an open source app that not just allows you to complete tasks, it guides you through as an actual assistant and motivates you throughout the way.

This may seem like such a trivial problem, but there are way too many cogs that actually spin the wheel. I usually do this in a phased manner. First, you start with defining your problem and stating your proposed solution. You try to figure out what part of the problem solution you need to prioritize, the edge cases and general flow. All this makes your product plan.

Next if you are builing an app (which we are doing in this case), we create a design. The design helps you visualize the problem. It can also help you identify edge cases, like error screens, erratic behaviour by the user etc.

Then we start coding paralelly on the apps (if there are multiple platforms) and the backend (if one is required). We bind it together by creating pipelines that help us deploy these to the end user. 

At the same time we do house keeping in the form of testing, code quality analysis and feedback/reviews.
